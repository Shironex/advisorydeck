# Ingest

`packages/ingest` turns upstream advisory data into the files in `data/`. It runs every hour in the Site workflow, which then deploys the site and the feed ([deploy.md](deploy.md)), and by hand with `pnpm ingest`.

## Running it

```sh
pnpm ingest --backfill            # first run: the cvelistV5 midnight baseline (about 650 MB, cached in .cache/ingest)
pnpm ingest                       # every later run: only what changed since the last one
pnpm ingest --offline             # no network: rebuild the outputs from data/sources
pnpm ingest --since 2025-11-16    # keep advisories first published on or after this date
pnpm ingest --skip ghsa           # skip a source (cve, ghsa, branches, kev, epss, nvd)
pnpm ingest --anonymous           # no GITHUB_TOKEN: run even when the run could exceed 60 requests an hour
```

Set `GITHUB_TOKEN` (for example `GITHUB_TOKEN=$(gh auth token) pnpm ingest`). The catalog makes one GitHub request per repository source and one per ecosystem for all `ghsa-package` sources together, plus a few release listings, and a query without a stored cursor (a new product, `--backfill`) can take several pages. Without a token GitHub allows 60 API requests an hour and caps each query at 5 pages, so before it starts ingest counts the worst case for the current catalog and cursors, reads the remaining anonymous budget from `GET /rate_limit` (which does not count against it) and refuses with exit code 2 when the run could exceed it. `--anonymous` runs anyway: a query cut off by the limit keeps its cursor and is finished on a later run. With a token the limit is 5000 (1000 for the Actions `github.token`). The token is only ever sent to `api.github.com`. A rate limit that resets within a minute is waited out; a longer one stops that source, keeps its cursor and still writes a consistent feed from what is stored (the run exits 1).

The hourly Site run uses the workflow's `github.token`. With 25 products it makes about 24 API requests an hour (17 repository queries, 5 ecosystem queries, the cvelistV5 release listing and the schedule keep-alive), far below the 1000 an hour that token allows; a new product adds one request (a repository source) or nothing (a package in an ecosystem already queried).

## What it writes

| Path                                                            | What                                                                                                                                 | Committed |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | --------- |
| `data/advisories/<id>.json`                                     | One advisory per cluster (`schemas/v1/advisory.schema.json`)                                                                         | yes       |
| `data/api/v1/manifest.json`, `data/api/v1/products/<slug>.json` | The feed exactly as published ([feed-contract.md](feed-contract.md)); the site copies `data/api/v1/` to `api/v1/`                    | yes       |
| `data/quality.json`                                             | Per advisory, the judgement calls made on messy upstream data (see below)                                                            | yes       |
| `data/sources/{cve,ghsa,endoflife}/`                            | Trimmed upstream records: only the fields ingest reads, no reporter names                                                            | yes       |
| `data/sources/kev/catalog.json`                                 | The KEV catalog: version, release date and the date each CVE was added                                                               | yes       |
| `data/sources/epss/scores.json`                                 | The EPSS score, percentile and date of every CVE in the feed (pruned to the feed)                                                    | yes       |
| `data/sources/nvd/<id>.json`                                    | NVD CVSS metrics for the CVEs that needed them (pruned to the feed)                                                                  | yes       |
| `data/state.json`                                               | The published floor and the cursors (last cvelistV5 release applied, newest `updated_at` per GHSA query, when EPSS was last fetched) | yes       |

Every run rebuilds the outputs from `data/sources`, so the outputs are a function of the stored records, the catalog and `notes/`. Files are written only when their bytes change, JSON keys follow the schema order, advisories are sorted newest published first then by id, and `generated_at` / `updated_at` move only when the product file they describe changes. A rerun with no upstream change leaves every byte as it was. `data/` is excluded from Prettier because the manifest etag is the sha256 of the exact bytes. `pnpm validate` checks `data/` with the same rules as the fixtures.

## Which product a record belongs to

The catalog's source index (`buildSourceIndex`) decides:

- **CVE records**: `cveMetadata.assignerShortName` must match a `cve-cna` source and an `affected[]` entry must match its `products` (and `vendor`, when set). `products: ["*"]` takes every product of the source's `vendor` (the Go CNA names each package, `net/http`, `crypto/x509`, as the product); it needs a `vendor`. Records from other assigners are only kept when a stored GHSA names them, for their CNA score and dates.
- **Repository advisories**: belong to the repository's product. When the `ghsa-repo` source lists `packages`, only entries with those names count (compared without case, whatever the ecosystem; `""` matches an entry without a name), and an advisory naming none of them is not about the product: Nextcloud's `security-advisories` repository lists Server next to apps such as `files_lock`. Otherwise, when some entries name the product itself (no language ecosystem, for example `Docker Engine` or `redis-server`) or a package the catalog gives the product, only those count; Go module entries of moby (`v2.0.0-beta.28`) are another version line and are skipped. When no entry does, all entries count (Coolify files some advisories under `npm:coolify`).
- **Global advisories**: an entry counts for the product that claims its `ecosystem:package`.

## Ranges

- Leading `v` and spaces are dropped; a version that does not fit the schema's version pattern, or does not start with a digit (NGINX Plus `R36`), makes the whole product's list unknown (`ranges: []`), never half a list. The one placeholder that is read is Metabase's `x.` major in GHSA records: `>= x.58.0, < x.58.28` is read once as `0.58.0` to `0.58.28` (open source) and once as `1.58.0` to `1.58.28` (Enterprise), and the ranges are joined; in the Enterprise reading a range from the first version starts at `1.0.0`.
- Java suffixes become semver: a dotted milestone or release candidate is a prerelease (Tomcat `9.0.0.M1` is `9.0.0-M1`) and `.RELEASE` is dropped (Spring `5.2.25.RELEASE` is `5.2.25`). In Python data (CVE `versionType: python`, the GHSA `pip` ecosystem), PEP 440 prereleases become semver ones (`3.15.0a1` is `3.15.0-a1`, `6.0rc2` is `6.0-rc2`); other schemes keep their letters (PostgreSQL's `17rc1`).
- `>= A, < B` is one range, and so are `>= A < B` (a space before `<` joins like a comma) and `>= A && < B`; an operator written after its version (Ghost: `v3.23.0>=`) or with its characters swapped (Valkey: `=>9.0.0`) is read as if written first; a comma between ranges or a hyphen range (`26.0.0 - 29.8.1`) separates them. A hyphen with no spaces between two versions with the same number of numeric parts is a range too (Oracle and MariaDB: `8.4.0-8.4.12` is `introduced: "8.4.0"`, `last_affected: "8.4.12"`), so it is not mistaken for a prerelease; `1.2.0-rc.1` and `5.15.0-122.132` stay one version, and a reversed pair is unreadable. Several bare upper bounds in a row (`<= v19.03.15, <= v20.10.27`) are one branch each, starting at the bound's `major.minor.0`; when the expression holds only upper bounds they are sorted first (Valkey writes `<= 9.1.1, <= 9.0.5, <= 8.1.9, <= 8.0.10`, newest first), so the lowest starts at `0` and the newest does not cover the patched releases of the older branches. A bound that is a prerelease of its branch's first release starts at that release's lowest prerelease (runc: `<= 1.5.0-rc.2` starts at `1.5.0-0`), not at an empty range from `1.5.0`. `> A` is read as `>= A`.
- CVE records: `version` plus `lessThan` gives `introduced` and `fixed`, `lessThanOrEqual` gives `last_affected`, a range inside the version field (`< 8.6.3`) is parsed as above. PostgreSQL's `0 lessThan 14.25` stays `introduced: "0"`. A wildcard line (PHP: `8.2.*` lessThan `8.2.35`) starts at its first release, `8.2.0`. When every affected line of an entry starts at its own last affected release and there are two or more (hackerone for Node.js: `22.23.3 lessThanOrEqual 22.23.3`, `24.22.0 lessThanOrEqual 24.22.0`), each is read as an upper bound, then per branch as below; a single such line stays one version.
- CVE records: unaffected entries change the reading only where they matter. When an unaffected version lies inside an affected range (Mattermost: `0 lessThanOrEqual 10.20.11` and `0 lessThanOrEqual 11.5.7` affected, `10.11.21` unaffected), the affected ranges are joined and each unaffected version is cut out with the rest of its line (`10.11.21` up to `10.12.0`), the highest one with every later release, which leaves one range per branch (`0` to `10.11.21`, `10.12.0` to `11.5.7`). When an entry lists only unaffected versions under `defaultStatus: affected` (Jenkins: `2.541 lessThan *`, `2.528.3 lessThan 2.528.*`), every other version is affected: `x.y.*` as a bound ends that line, so this reads as before `2.528.3` and from `2.529.0` to `2.541`. When an unaffected entry cannot be read or ordered (Mattermost lists desktop builds such as `6.2.3.0` next to server versions) or a cut cannot be written as a range, the product's versions are unknown. Unaffected versions that lie after the ranges, the usual shape, change nothing.
- CVE records of semver products: an open range (`1.25.0 lessThan *`) next to later lines that each have a fix (`1.30.0 lessThan 1.30.6`, `1.31.0 lessThan 1.31.7`, F5 for nginx) ends on the branch before the next listed start (`last_affected: "1.29"`), so the patched 1.30.6 and 1.31.7 are not reported affected. It stays open when the next start is not the first release of a line or a later line has no fix. GHSA records of semver products follow the same rule across their entries (Portainer: `>= 2.39.0` with no fix yet for the LTS line next to `>= 2.40.0, < 2.45.2` ends at `last_affected: "2.39"`), and a closed range with no patched version (`>= 2.39.0, <= 2.39.8`) stays closed.
- One upper bound per branch, written as ranges that all start at the first version (n8n: four entries `< 1.123.96`, `< 2.47.6`, `< 2.48.3`, `< 3.2.2`; Rocket.Chat CVE: `0 lessThan 8.8.0`, `0 lessThan 8.7.1`, ...), is one range per branch: sorted, the lowest keeps `0` and each next range starts where the line of the previous bound ends, on the next minor within a major (`2.48.0`) or the next major across majors (`2.0.0`, `3.0.0`). An unlisted line between two listed lines of a major (Keycloak `26.5` between `26.4.14` and `26.6.5`) or a whole unlisted major (Node.js 23) stays affected up to the next listed fix; minors after the last listed line of a major are later releases that carry the fix. When a bound is the first release or a prerelease of the line it starts on (`< 8.8.0` after `< 8.7.1`), the range starts at that release's lowest prerelease (`8.8.0-0`). Two bounds on one branch, a lower bound other than `0` or an open range leave the ranges as written.
- GHSA: a single patched version fills an open range. When it is later than the written upper bound (`< v4.0.0-beta.436` patched in `4.0.0-beta.437`, `<= 4.0.0-beta.448` patched in `4.0.0-beta.451`), the range ends at the patched version: the stricter reading, so a version in between is reported affected rather than silently not affected. When the patched version equals an inclusive upper bound (Ghost: `>=0.5.3 <= 6.50.0` patched `6.50.0`), the patch wins: the range ends at `fixed: "6.50.0"`, with a note. A bare version next to a later patch (`v4.0.0-beta.428`, patched `4.0.0-beta.429`) means every version before the patch. A bare version later than its patch (`v4.0.0`, patched `4.0.0-beta.469`) is unknown.
- GHSA: one upper bound from the first version next to a patched list whose newest version closes it (Valkey: `<= 9.0.2` patched `9.0.3, 8.1.6, 8.0.7, 7.2.12`) names only the newest branch, so it is read like the per-branch list below: the first range from `0`, each next from `x.0.0` on a new major or `x.y.0` within one. When the newest patch is on another branch the range stays as written.
- GHSA `All` with one patched version per branch (`6.2.20, 7.2.11, 7.4.6, 8.0.4, 8.2.2`) becomes one range per branch: the first from `0`, each next from `x.0.0` on a new major (so an unpatched `7.0` line is covered) or `x.y.0` within a major. `All` or `TBD` alone carries no range: unknown.
- GHSA lower bounds with a patched list of the same length (Nextcloud: `>= 32.0.0, >= 33.0.0, >= 34.0.0` patched `32.0.12, 33.0.6, 34.0.1`) are paired after sorting, each patch after its lower bound and before the next one. Lower bounds that do not pair that way (Next.js: four lower bounds, ten patches) are unknown; lower bounds with no patched version at all stay open.
- A Go module with a major suffix only holds that major: an open lower bound on `github.com/traefik/traefik/v2` starts at `2.0.0`, so Traefik 1.x users get no false alarm.
- Within a cluster, each product takes its ranges from the most trusted source in catalog order whose ranges are all bounded, else the most trusted one with any ranges, else unknown. For Redis this prefers a GHSA per-branch list over the CVE record's single `< 8.6.3`, and the CVE range over a GHSA that says `All`.

Each of these judgement calls on a real record is listed in `data/quality.json`, so a reviewer can check them against the vendor page.

## Clusters and fields

- GHSA records link to their CVE (`cve_id`, `identifiers`), and a CVE record links the GHSA its references point at (`github.com/<owner>/<repo>/security/advisories/GHSA-...` or `github.com/advisories/GHSA-...`), as VulnCheck and GitHub records do; a CVE record citing several GHSAs links none of them and says so in `data/quality.json`. Linked ids form one cluster, so a repository advisory without a CVE id and the CVE filed for it later are one advisory, and two CVEs filed for one GHSA share it. The id is the lowest CVE id, else the GHSA id; every other id is in `aliases`.
- `title`: the CNA title, else the GHSA summary, else the first sentence of the description. `summary`: the CVE description, else the GHSA description (truncated to the schema limits).
- `severity`: the CNA's CVSS (3.1, then 4.0, 3.0, 2.0), else the GHSA's CVSS, else NVD's own (Primary) CVSS, else another NVD metric, else the GHSA severity word without a score, else `unknown`.
- `published_at` is the earliest of the cluster, `modified_at` the latest.
- `kev`: `listed` when any CVE id of the cluster is in the catalog, `added_at` the earliest date added, `checked: true` once the catalog was read. When no catalog was ever read (first run with KEV down, or `--skip kev` on an empty store), every advisory says `checked: false` and the run warns; `pnpm validate` refuses such a `data/`. A stored catalog is reused when a later fetch fails.
- `epss`: the highest score among the cluster's CVE ids, or `null` when EPSS has not scored any of them. Scores drift a little every day, so a stored score is replaced only when the percentile moves by 0.01, the probability by a tenth (and at least 0.001), or it crosses the 0.95 percentile. That keeps a daily run from rewriting every file.
- `revision` hashes severity level, ranges, `kev.listed`, the EPSS signal (only whether the percentile is 0.95 or above) and the note, so filling or refreshing a score does not repost anything.
- `sources` adds a `kev`, `epss` or `nvd` record for each CVE id the enrichment used.
- `note` is the reviewed note in `notes/<id>.md`, if any (`toFeedNote`).
